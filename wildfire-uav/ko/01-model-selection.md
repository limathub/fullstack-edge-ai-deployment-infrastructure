# 01 — 모델 선정 & 평가 방법론

---

## 시작 조건

- 라벨 데이터도 벤치마크도 없이 시작. 과제가 무엇인지에 대한 명확한 합의도 없었음.
- 첫 번째 실질적 결정은 **문제를 좁히는 것**. "불이 정확히 어디 있는가"가 아니라 "이 프레임에
  불이 있는가"로. 위치 추정 정밀도는 명시적으로 뒤로 미루고, 속도나 모델 크기보다 희미한 초기
  연기를 잡는 정확도를 우선. 화재 초반 10분을 놓치면 빠르게 도는 것에 의미가 없기 때문.

---

## 서베이

15개 이상의 모델 계열을 느낌으로 비교하는 대신 **단일 리더보드**에서 같은 기준으로 비교.

| 계열 | 유형 | 결과 |
| :--- | :--- | :--- |
| zero-shot open-vocabulary 검출기 | 텍스트 프롬프트 기반 검출 | **채택** — 희미한 초기 연기에서 선두 |
| 파인튜닝 supervised 검출기 | supervised | 데이터셋이 만든 상한에서 서로 동률 |
| 비전-언어 QA 모델 (아키텍처 3종) | 이미지→텍스트 응답 | 참고용으로는 유용, 미세 연기는 놓침 |
| 산불 특화 세그멘테이션 | segmentation | 기각 — 감시탑 영상으로 학습되어 도로를 연기로 읽었고, 엣지 예산에 비해 지연도 너무 컸음 |
| 사전학습 open-vocabulary 검출기 (COCO/LVIS 계보) | zero-shot | 기각 — 검출 0건, 사전학습에 화재/연기 개념 없음 |

더 큰 모델들이 놓친 희미한 초기 연기를 zero-shot 검출기가 잡아냄. 과제별 학습 없이 선두를
유지했고, 그대로 프로덕션 베이스라인으로 채택.

---

## 채점 기준, 그리고 채점할 벤치마크

- 일반적인 P/R/F1(정밀도·재현율·F1)에 **프레임 단위 strict 지표**를 더한 기준으로 채점.
  오탐(false positive)이 하나라도 있는 프레임은 오답으로 침. 오탐이 하나 섞인 프레임을 부분
  정답으로 치는 것은 실제 운용 단계의 요구와 맞지 않기 때문.
- 벤치마크는 공개 데이터로 채울 수 없었음. 그래서 영상을 직접 찍고, 자체 호스팅한 어노테이션
  플랫폼에서 직접 라벨링함([02장](./02-data-pipeline.md)).
- 프레임을 **맥락별로 분류.** 시점, 거리, 화재 진행 단계 등. 이 분류를 바탕으로 실제 현장 운용
  조건과 일치하는 데이터의 평가 비중을 높임. 그래야 리더보드 점수가 공개 데이터 평균이 아니라
  실제 배포 환경에서의 성능을 대변할 수 있기 때문.
- 최종 홀드아웃 벤치마크는 **어떤 후보 모델도 학습에 쓴 적 없는** 4개 출처로 구성하고, 소스별
  채점 규칙을 확정.

만들면서 더 미묘한 문제 두 가지가 드러남.

**어노테이션 스타일이 IoU를 왜곡함.** 사람 라벨러는 성향에 따라 원본 데이터셋보다 여백이 넓은
느슨한 박스를 그리기도 하고, 확실한 부분만 짚는 타이트한 박스를 그리기도 했음. 그래서 IoU 임계값
하나가 어디서나 통한다고 가정하지 않고, 실제 알고리즘을 영상에 얹어 돌려 보며 적절한 임계값을 확정.

**특정 크기 이하의 정답을 제외하면 지표가 왜곡됨.** 작은 객체를 정답에서 빼면 맹점이 생김. 모델이
그 작은 불씨를 정확히 찾아내도 정답에 없으니 오탐으로 처리되어 F1이 떨어짐. 이 왜곡을 숨기지 않고
최종 점수 옆에 함께 기록하고, 크기가 작은 검출은 직접 눈으로 보고 판단.

---

## 데이터의 맥락이 성능을 갈랐음

- 학습 데이터를 충분히 늘리자 검증 mAP는 올랐지만 홀드아웃 하드케이스는 움직이지 않았음. 같은
  검출기 계열의 파인튜닝 4세대가 같은 사례를 같은 비율로 놓침. 병목은 아키텍처가 아니라
  데이터였음.
- 이유는 공개 데이터의 성격에 있음. 공개 산불 데이터셋 5종을 시점 적합도로 조사해 보면 쓸 만한
  것이 감시탑 영상이거나 이미 크게 번진 불의 우연한 촬영본임. 사진으로 남는 불이 그런 불이기 때문.
  조기 검출에 필요한 영역, 즉 위에서 근거리로 본 작고 희미한 초기 화재는 대규모로 수집된 공개
  데이터가 없었음.
- 그래서 자체 수집으로 가되, 반복할 수 있을 만큼 싸게 만들기로 함(→ [02장](./02-data-pipeline.md)).

## 프롬프트 엔지니어링

이 단계에서 가장 적은 비용으로 시도할 수 있는 최적화인 프롬프트 튜닝도 여러 방면으로 시도함.

- **프롬프트 설계는 아키텍처에 종속됨.** late-fusion과 cross-attention 등 서로 다른 아키텍처에
  함께 잘 듣는 프롬프트 설계는 찾지 못했고, 모델 구조에 따라 다른 접근이 필요했음.
- **복잡한 프롬프트가 항상 좋지는 않음.** 20가지가 넘는 프롬프트 sweep 결과, 복잡한 구성(예를
  들어 연기와 구름을 함께 넣어 연기에 가까운 것만 고르게 하는 식)이 오히려 단순한 구성보다
  밀리는 경우가 많았음.
